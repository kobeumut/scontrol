# MEMORY.md

Durable project context that is not obvious from the code. Read it together with `AGENTS.md`. Status and checklists live in `TASK.md`; this file records decisions and why they were made. Last reviewed: 2026-11-03.

## Decisions

- **Docker is a Dokploy-style deployment workflow, not a container dashboard.** Per the plan's research summary, HestiaCP and CloudPanel both lack Docker support. A Portainer-style dashboard was rejected in favour of application and Compose deployments (`TASK.md`, Docker section).
  - How to apply: do not add `docker run` or raw container CRUD endpoints. Model work as projects and Compose deployments.
- **Docker, Mail, and Antivirus are opt-in at install time and compile-time features.** They are off by default. The base install stays small (the plan targets ~50 MB RAM) and installs no packages nobody asked for.
  - How to apply: new optional code goes behind a `panel-agent` feature. Do not make it unconditional.
- **Host commands are typed argv only.** This is the plan's core security requirement: no shell, no string-built commands, least privilege.
- **Auto-PR commits only allow-listed, non-secret config.** The watcher runs as root and pushes to GitHub, so the allow-list and the secret-key rejection in `install/auto-pr.sh` form a security boundary.
- **Offline SQLx metadata is committed on purpose (`panel/.sqlx`).** Builds with `SQLX_OFFLINE=true` need no database.
  - How to apply: after any SQL change, run `cargo sqlx prepare --workspace` and commit the updated `.sqlx` files, or offline builds break.
- **Dokploy is research input, not a code source.** Use its conceptual model only. Do not copy its code.
- **The deployment queue is PostgreSQL, not memory or Redis.** Dokploy's self-hosted queue is in-memory: it loses jobs on restart and runs effectively one build at a time. Here `compose_deployments` rows are the jobs (decided 2026-11-03, `PLAN.md` §3).
  - How to apply: new deploy-like work (webhooks, previews, rollbacks, backups) enqueues rows and lets the workers run them. Keep per-project serialisation in the claim query.
- **Secrets never ride in queue rows.** Environment values are written to the agent through a separate RPC before a job is queued, so a durable queue does not mean secrets at rest in PostgreSQL.
- **Webhook secrets are derived, not stored.** The secret is HMAC(server key, project ID + nonce), and only the nonce is in PostgreSQL, so a database dump does not leak deploy triggers. The server key comes from `PANEL_COOKIE_KEY`, so rotating that key invalidates every webhook secret (decided 2026-11-03).
- **Stored secrets are sealed with `PANEL_SECRET_KEY`, separate from the cookie key (decided 2026-11-03).** Notification credentials are the first secrets panel-api must read back, so they are AES-256-GCM sealed (`services/secret_box.rs`) with the row ID and kind as associated data. A separate key lets operators rotate `PANEL_COOKIE_KEY` (logging everyone out) without losing stored secrets. Installs from before the key existed fall back to the cookie key; the installer never adds the key to an existing env file, because that would make already-stored secrets unreadable.
  - How to apply: seal every new stored secret that panel-api itself must read back (registry, S3, GitHub App keys) with `SecretBox` and row-bound AAD. Never return it; report `has_secret` instead.
- **Git deploy keys and HTTPS tokens live on the agent, not in PostgreSQL (decided 2026-11-03).** Only the agent ever uses them, so they follow the environment model: written once through a dedicated RPC, kept in 0600 files in the project directory, and absent from the database (which stores the public key and the token's host). The private key is generated on the agent and never leaves it.
  - How to apply: a credential that only host commands need goes to the agent this way. Seal it in PostgreSQL only when panel-api has to use it (for example to mint a GitHub App token).
- **GitHub App keys are sealed in PostgreSQL; their tokens are per deployment (decided 2026-11-03).** panel-api must sign the App JWT itself, so this is the case the rule above reserves for `SecretBox`. Tokens are minted when a queue worker starts the job, scoped to the one repository with `contents: read`, sent with that deploy request only, and deleted by the agent afterwards, so the durable queue never holds a credential and a leaked token expires within an hour. RSA signing uses `ring` (already in the tree through rustls), not the `rsa` crate.
  - How to apply: a new short-lived credential follows the same path, `DeployComposeProjectParams` plus an agent-side 0600 file that is removed when the deployment ends.
- **Builders never receive build variables, and their outputs stay out of the checkout (decided 2026-11-03).** Nixpacks, Railpack, and pack take build variables only on argv, which every local user can read, so the environment is runtime-only for builder apps. Anything a builder writes besides the image goes to the agent-owned `build/` directory, because a root-owned write into the checkout could follow a committed symlink.
- **Static sites publish copies, not the checkout (decided 2026-11-03).** Nginx would follow a symlink in the repository or one created by the build to a host file. Releases are fresh lstat-based copies of regular files only, under `/srv/scontrol/static` (the Nginx worker cannot traverse `/var/lib/scontrol`), and the vhost adds `disable_symlinks on` as a second layer.
- **Git helpers are the agent binary itself, not shell snippets (decided 2026-11-03).** `GIT_SSH_COMMAND`, `core.sshCommand`, and `!`-style credential helpers are run by Git through `sh -c`. Instead the agent sets `GIT_SSH` and `GIT_ASKPASS` to its own executable plus `SCONTROL_GIT_HELPER=ssh|askpass`; `main` detects that before logging starts. The ssh helper `exec`s `ssh` through `exec::exec_replace` (allow-listed, covered by the source scan). The askpass helper answers only for the host the token was saved for, so a redirect to another host gets nothing.
  - How to apply: a new Git or SSH integration adds a helper mode or typed argv, never a command string for Git to interpret.
- **Processes are spawned only through an allow-list in `adapters/exec.rs`.** A shell or interpreter is never on the list, and a source-scan test fails the build if code elsewhere spawns processes or names a program that is not a literal on the list (2026-11-03).
  - How to apply: add a new host tool to `ALLOWED_PROGRAMS` in the same change that calls it. Pass secrets through stdin (`run_with_stdin`), env, or 0600 files, never argv.
- **Live logs are a streamed RPC, not polling.** `follow_compose_logs` is the one agent request that answers with many lines; closing the connection is the stop signal. Redaction runs before search so search cannot reveal masked values.
- **Applications are a Compose source, not a separate table (decided 2026-11-03).** An application is `ComposeSource::Application`, which the agent renders into a generated Compose file. That reuses the queue, logs, environment, domains, webhooks, and Git access with no migration, and keeps one deploy engine. The project environment reaches the container through `env_file` pointing at the 0600 `env` file.
  - How to apply: new application options become typed `ApplicationSpec` fields rendered through `serde_yaml` values, validated in `ApplicationSpec::validate` (shared by API and agent). Never template YAML strings. Health checks stay exec-form (`CMD`).
- **The Compose policy treats every host path as hostile (decided 2026-11-03).** `docker compose` runs as root, so `env_file`, build contexts, secret/config files, `include`, `extends.file`, `label_file`, and volume `driver_opts` can all read host files. Relative paths are allowed only when they resolve, symlinks included, inside `code/`.
  - How to apply: when Compose gains a key that names a host path, add it to `compose_policy` and the symlink resolution in the same change.
- **Layered variables are sealed in PostgreSQL and merged by panel-api at deploy time (decided 2026-11-03, D2).** Project and environment variables are shared by many services, and a merge needs every layer, so panel-api must read them back: by the stored-secret rule above they are sealed with `SecretBox` (AAD = layer, scope id, key) in `env_variables`. The service layer is stored the same way so the worker can merge all three in memory and send the result through the existing `write_compose_environment` RPC just before the deploy RPC. This replaces "service environment only on the agent" for services created or saved since migration 0008.
  - Why not merge on the agent: the agent would need the project and environment layers on disk per service, duplicated across services, and the merge rules would live in root code. One write RPC keeps the agent simple.
  - Backward compatibility: services from before 0008 have `env_layered = false`. Their values are only on the agent, so the worker must not overwrite that file; they inherit nothing until the operator saves their variables once. Never add an RPC that reads env values back from the agent to "adopt" them.
  - How to apply: responses, audit rows, and errors name keys only. Overridden inherited values still go to the agent as `masked_values` (0600 `env.masked`), because a value that is not in the container can still show up in build output. Updates accept a key without a value to keep the stored one, so the UI never needs to read values.
- **Database services are a Compose source with sealed credentials, and outside access goes through the host Nginx (decided 2026-11-04, D3).** Like applications, `ComposeSource::Database` reuses the queue, logs, and history; the agent renders it from a fixed per-engine template. panel-api must show the password to the operator, so it is sealed with `SecretBox` in `database_services` (not an env layer, which a user could edit or delete) and travels to the agent per deployment like GitHub App tokens.
  - Why not publish on `0.0.0.0` with a UFW rule: Docker-published ports bypass UFW, so the rule would not protect anything. A host Nginx `stream` server is filtered by UFW and also enforces the same `allow` list itself.
  - Redis has no environment variable for its password and argv is forbidden, so the agent writes a 0400 config (owned by the image's `redis` user, UID 999) and mounts it as a Compose secret. The agent's own absolute files (`env`, `db.env`, `redis.conf`) are the only absolute paths `compose_policy` accepts.
  - How to apply: a new engine is a template in `panel_core::database_services` (version allow-list, data path, env, password-free exec health check) plus a render test. Never add a password-bearing health check or command.
- **Routing uses the host Nginx, not Traefik.** Compose domains publish the service on a loopback port (40000–49999) and get a generated vhost. That avoids an extra always-on proxy container and Docker-label rewriting of user Compose files.
  - How to apply: do not inject labels into, or rewrite, user Compose files. Add routing features (redirects, basic auth, path prefixes) as typed vhost options.

- **Scheduled jobs are systemd timers that run the agent binary, not a command line (decided 2026-11-04, D3).** `ExecStart=` is parsed by systemd with its own quoting and `%` specifiers, so the job's argv never goes into a unit: the unit runs `panel-agent run-scheduled-job <slug> <id>`, and the helper reads the argv from a 0600 `job.json` and runs `docker compose exec -T` with it. Everything else written into a unit is a UUID, a slug, a checked path, or a calendar value from a narrow character set.
  - Runs are recorded by the helper next to their logs and collected by panel-api, because the helper has no database access and a root process should not get it. The collector upserts so that each finished run is stored, and notified, exactly once.
  - Stopping the `docker compose exec` client does not stop the process inside the container. Each run carries `SCONTROL_JOB`/`SCONTROL_JOB_RUN` in its environment, and the agent stops container processes with that marker (found through `docker top` host PIDs and `/proc/<pid>/environ`) on timeout, before the next run, and on removal. Never stop them by name or with a container-wide signal.
  - Jobs run only inside a project's containers. Host jobs as root would be arbitrary root execution from the panel, and the per-site `cron` adapter already covers site users.
  - How to apply: a new scheduled feature (backups, Docker cleanup) adds a helper mode or reuses this one with typed parameters, never a command in a unit file or crontab.

## Request statistics and Docker cleanup (GENE-74)

- Decision: the agent's access-log reader keeps no state; panel-api owns the inode and offset and commits them with the buckets.
  - Why: the database is the one place that can make "count the requests and move the cursor" atomic, and a stateless agent survives restarts and rotation without a second cursor file.
  - How to apply: any future incremental reader (metrics, mail logs) passes its cursor in and out the same way.
- Decision: `$host` is client-controlled, so hosts are normalized and capped per chunk, with the rest counted as `_other`.
  - Why: a flood of random `Host` headers must not create unbounded rows.

## Server and container metrics (GENE-73)

- **Metrics are sampled in the agent from kernel files and stored by panel-api as a downsampled ring (decided 2026-11-04, D4).** `docker stats` and tools like `top` spawn a process per sample and cost far more than the ≤ 1 ms budget; reading `/proc` and cgroup v2 directly costs ~0.4 ms. The agent keeps only the latest snapshot in memory (it has no database), and panel-api pulls it every 30 s, so a panel-api outage loses samples rather than queueing them on the root side.
  - Container metrics are stored per Compose service of a panel project (`compose_project_id`, `service`), not per container ID, because IDs change on every redeploy. Containers of other Compose projects on the host are not stored. Container CPU uses the `docker stats` convention (100 % = one core).
  - Alerts are edge-triggered with a consecutive-sample count and a hysteresis band, and their state lives in `metric_alert_state`, so a restart neither repeats nor drops an alert. A metric that disappears (unmounted disk, removed service) is forgotten without a "resolved" message.
  - How to apply: a new metric is a parser in `panel_core::metrics` with a synthetic-file test, a field in the snapshot, and (if alertable) a `watched_metrics` entry with a stable key. Never add a process spawn to the sampler.

- **Rollbacks start pinned images from an agent-held release, checked against a credential-free snapshot (decided 2026-11-04, D5).** Tags like `scontrol-app/<slug>:latest` or a Compose `image:` move with every deployment, so each successful deployment tags the image ID each running service uses as `<slug>/<service>:deploy-<id>`. The agent keeps the deployed Compose file (0600) because it may contain literal secrets; PostgreSQL gets only a sanitized `DeploymentSnapshot` plus the file's SHA-256, and a rollback must match both the hash and the image list of the agent's record, so a tampered database row cannot point the agent at another image.
  - Why the current environment: values are write-only and must never be snapshotted, so a rollback reverts code and images, not configuration. Files the Compose file reads from the checkout (bind mounts, `env_file`) also come from the current checkout; domains are the current ones.
  - Why `pull_policy: never` and no `--build`: a rollback must be a container switch, and a same-named image in a registry must never replace the pinned local one.
  - Database services are excluded (an older engine on newer data files can corrupt them); static sites have no images (rolling back their kept release directories is a follow-up).
  - How to apply: a new source kind either produces images that can be pinned per service or is added to `supports_rollback` exclusions; never put an environment value into a snapshot field.
## Pull request previews (GENE-76)

- **A preview is an ordinary Compose project created from the parent, driven by the parent's webhook (decided 2026-11-04, D5).** Reusing the project, queue, domain, and deployment machinery means previews get logs, cancellation, masking and per-project serialisation for free; the only additions on the agent are resource limits in the generated override, a named-certificate option for vhosts, and volume removal for ephemeral projects.
  - Why same-repository requests only: a preview runs the request's code with the parent's environment variables. Someone who can push a branch to the repository can already change what production deploys; a fork author cannot, so fork requests are ignored (closing one is still handled).
  - Why the parent's service layer and not copies: copying sealed values would need re-sealing under new AAD and would go stale; the worker merges the parent's layers at deploy time instead.
  - Why teardown is asynchronous with a `closing` state: `docker compose down` can outlast a Git host's webhook timeout, and a preview whose deployment is still running must be cancelled before removal. The sweeper retries until the row is gone, so a crash in between leaves nothing behind.
  - Why comments carry no error text: pull request comments are visible to everyone who can read the request, and deployment errors can name hosts, paths, or registry details.
  - Limits are set both as service keys (`mem_limit`, `cpus`, `pids_limit`) and as `deploy.resources.limits`: Compose refuses two different values, and an override replaces either form the application set.
  - How to apply: anything that lets previews deploy from private repositories over deploy keys or HTTPS tokens must copy those credentials agent-side; never send them through panel-api.
